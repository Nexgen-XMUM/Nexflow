# Orbyte Smart Yield

> 打烊前 5 秒，把卖不完的面包变成现金和减碳。
> Orbyte SME Challenge 参赛项目，对应联合国 **SDG 12.3（减少食物浪费）**。

---

## 1. 要解决的问题

马来西亚的烘焙店老板（我们的用户画像：Uncle Wong）每天晚上快打烊时，总会剩下一批牛角包和蛋糕。

- 丢掉：白白损失成本，还造成食物浪费。
- 想清仓：店员已经很累，没精力算“打几折才不亏本”，也没时间写文案、发 WhatsApp 给熟客。

结果就是：东西被丢掉，而老板从来没算过这笔账。

## 2. 我们的方案

店员只需要报一个数量，系统自动完成：**算保本折扣 → 写促销文案 → 送老板审批 → 老板一键批准后群发 → 记录成果**。老板始终掌握最终决定权。

## 3. 五步自动化旅程

| 步骤 | 在产品里对应什么 |
|---|---|
| 1. Trigger 触发 | 店员在“打烊盘点”页输入剩余数量，点“提交盘点” |
| 2. Connected data 关联数据 | 系统调取商品成本价/原价、50 位熟客名单、碳排系数 |
| 3. Decision logic 决策逻辑 | 定价引擎（纯代码）算清仓价；文案引擎生成 WhatsApp 文案 |
| 4. Human approval 人工审批 | 老板在看板页查看草稿，可修改文案，点“批准并群发”或“拒绝”；店员角色无权批准 |
| 5. Visible outcome 可见结果 | 手机模拟器显示群发和熟客回复；看板数字更新；活动日志新增一条记录 |

## 4. 目前已完成的功能（v1）

- 三个页面：打烊盘点、老板看板、活动日志，外加 WhatsApp 手机模拟器
- 快速输入识别：输入 `12 croissants, 5 chocolate slices` 即可自动填数量
- 角色权限：店员（Siti）不能批准，老板（Uncle Wong）才可以
- 文案可编辑、可重新生成（目前为 3 套 Manglish 模板）
- “这些数字怎么算的”可展开说明，方便评委检查
- 支持手机屏幕和深色模式

**v1 只有前端**：所有逻辑暂时在 `frontend/index.html` 里用 JavaScript 模拟，后端接口见第 7 节（计划中）。

## 5. 怎么运行

不需要安装任何东西。

1. 下载或 clone 本仓库
2. 双击打开 `frontend/index.html`（用 Chrome 或 Edge）
3. 点“提交盘点”，再切到老板看板点“批准并群发”

想用本地服务器打开的话：

```bash
cd frontend
python -m http.server 8000
# 然后用浏览器打开 http://localhost:8000
```

页面里的字体来自 Google Fonts，没有网络时会自动换成系统字体，不影响使用。

## 6. 核心逻辑

所有金额和碳排计算都是普通代码，**没有任何一步交给 AI**。

```
清仓价   = max(原价 × 50%, 成本 × 1.2)，取到 RM0.10   → 永远高于成本价
预计售出 = 剩余数量 × 80%                               → 80% 是假设值
预计挽回 = 预计售出 × 清仓价
净利润   = 预计挽回 − 预计售出 × 成本
减碳     = 预计售出的重量(kg) × 2.5 kg CO₂e/kg
```

例子（默认数据）：

| 商品 | 剩余 | 成本 | 原价 | 清仓价 | 预计售出 | 预计挽回 |
|---|---|---|---|---|---|---|
| Croissant | 12 | RM2.00 | RM6.00 | RM3.00 | 10 | RM30.00 |
| Chocolate Cake Slice | 5 | RM3.50 | RM9.00 | RM4.50 | 4 | RM18.00 |
| **合计** | | | | | | **RM48.00**，净利润 RM14.00，减碳约 2.95 kg CO₂e |

## 7. 接口设计（计划中，v2 由 Flask 后端实现）

v1 的逻辑都在前端。v2 会把核心逻辑搬到后端，前端通过下面 6 个接口调用：

| 方法 | 路径 | 作用 | 对应旅程 |
|---|---|---|---|
| POST | `/api/stocktake` | 提交打烊盘点，返回价格表、预计挽回金额、减碳量和文案草稿 | 1、2、3 |
| POST | `/api/copy` | 为草稿重新生成促销文案（v3 接入 LLM） | 3 |
| POST | `/api/approve` | 老板批准，执行群发，写入日志（需要老板角色） | 4、5 |
| POST | `/api/reject` | 老板拒绝草稿，写入日志（需要老板角色） | 4、5 |
| GET | `/api/dashboard` | 获取看板累计数字（挽回营收、减碳、避免浪费、促销次数） | 5 |
| GET | `/api/log` | 获取活动日志列表 | 5 |

`POST /api/stocktake` 的请求和返回示例：

```json
// 请求
{
  "role": "staff",
  "items": [
    { "id": "croissant", "qty": 12 },
    { "id": "choc", "qty": 5 }
  ]
}

// 返回
{
  "draft_id": "d_001",
  "items": [
    { "id": "croissant", "qty": 12, "price": 3.0, "sold": 10, "revenue": 30.0 },
    { "id": "choc", "qty": 5, "price": 4.5, "sold": 4, "revenue": 18.0 }
  ],
  "revenue": 48.0,
  "profit": 14.0,
  "co2_kg": 2.95,
  "copy": "Bossku! ..."
}
```

`POST /api/approve` 的请求示例：

```json
{ "draft_id": "d_001", "role": "owner", "copy": "老板可能修改过的最终文案" }
```

## 8. AI 的使用与风险防线

- **AI 只负责润色文案**，不参与任何价格或数学计算。
- 所有折扣由规则代码计算，并且有保底价（成本 × 1.2），所以不会因为 AI 出错而亏本卖。
- 任何群发都必须经过有权限的人批准，批准前老板可以修改文案。
- v1 的文案引擎是模板；v3 计划接入大语言模型（例如部署在 Runpod 上的开源模型），接入后价格逻辑保持不变。

## 9. 数据与假设说明

- 所有商品、客户、历史记录、看板起始数字都是**合成数据**，仅用于演示。
- “促销后 80% 能卖出”是**假设值**，不是实测结果，在 `index.html` 的 `DATA.sellThrough` 修改。
- 碳排系数 2.5 kg CO₂e/kg 是估算值，正式提交前需要补上来源。
- 看板上显示的 WhatsApp 群发和熟客回复都是模拟，没有真的发送任何消息。
