# Hackathon 演示交付标准

更新日期：2026-10-22。
来源：qbc 在总控对话中明确要求；这是比赛原型，时间有限，能模拟的就模拟，优先完成演示和宣传。

## 后续工作的默认原则

- 目标是电脑版 Web 在比赛电脑上顺畅演示，不追求生产上线或把思维导图全部实现。
- 三位队友已在进行的任务继续收尾，不新增一轮功能任务。
- 能复用现有实现就复用；支付、WhatsApp、取餐、积分、机构接收等可使用明确标注的模拟流程。
- 业务规则以演示故事前后一致为准，不追求复杂政策、全面风控、所有异常场景或完整历史账本。
- 保留基本输入校验、正确金额和密钥保护；只优先修复会卡住演示、导致明显错误或泄露 Key 的问题。
- 页面和宣传区分真实实现、模拟场景与未来计划；示例收入不宣传为真实收入，环保估算不宣传为已认证碳资产。
- 暂停真实支付、真实 WhatsApp 集成、完整登录权限、手机 App、采购预测、品牌合作结算和碳交易开发。
- 部署只有在赛事要求或演示方式需要时才做；本地运行和备用录屏足以支持当前默认方案。

## 足够参赛的演示

1. 输入示例余货，看到价格、促销文案和环保估算。
2. 老板审核，WhatsApp 模拟器出现促销消息。
3. 展示盲盒方案，模拟顾客购买、取餐和积分变化；不要求真实付款。
4. 展示剩余食品的捐赠或能源处理建议，模拟人工确认去向；不要求真实联系机构。
5. 看板显示与演示场景一致的结果，样例数字注明演示。

## 三位队友的收尾目标

- KD：救援页面能展示余货去向和模拟交接，复用已有接口；不继续做碳交易和真实物流。
- 购买流程负责人：能完成一次模拟购买、取餐和积分展示；已有后端可用则复用，不为边界情况大改架构。
- 网页与演示负责人：统一页面入口、简化比赛操作、整理看板与启动步骤，配合制作宣传和录屏。
- 仅当问题阻止正常演示时，才扩展原定修复范围。

## 收工条件

- 在比赛用电脑上按固定步骤完成一次约三分钟的演示，没有卡死或明显矛盾。
- 准备一份简短讲稿或幻灯片：商家痛点、演示流程、商家价值、商业设想和未来计划。
- 准备备用演示录屏与关键截图，模型或网络不可用时可用本地模板继续展示。
- 清楚说明哪些功能是模拟；商业合作与碳资产交易只在未来计划中介绍。
- 完成以上内容后停止加功能；是否还需提交特定比赛材料，以主办方实际要求为准。
